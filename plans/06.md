# Plan for #6: Add PATCH /api/runs/:id/status with allowed transitions

## Goal
Users can advance a run from `planned` to `running` and then to `done`. The change adds a status-transition endpoint without changing the rest of the run API or default seed data.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- Confirmed: `src/runs.ts` — `RunStatus` and `RunStore` own the status model and in-memory state; change: yes.
- Confirmed: `src/app.ts` — route handlers are the HTTP layer; change: yes.
- Confirmed: `test/app.test.ts` — unit tests exercise the API and should cover success, invalid transition, and 404; change: yes.
- Confirmed: `docs/tickets/06-run-status-transitions.md` — issue spec defines allowed transitions and error contract; change: no.
- Confirmed: `README.md` — API table should mention the new endpoint if it is included in the public contract; change: likely yes.
- Plausible: `public/index.html` — user interface may eventually render status; not required by issue, verify before touching; change: no.
- Open: none.

## Tests
- `test/app.test.ts`: add PATCH happy path for `planned -> running` and `running -> done`.
- `test/app.test.ts`: add invalid transition assertion with 409 and `{ error: "invalid transition", from, to }`.
- `test/app.test.ts`: add unknown-id 404 test for PATCH status.

## Environment contract
No environment variables are added or required; no `src/config.ts` or `k8s/configmap.yaml` change.

## Risks

- Route ordering and 404/409 handling must not shadow unknown-run or JSON-body errors.
- Pipeline risk is low: unit tests, build, and smoke checks should pass; browser and deploy remain unaffected unless API contract is broken.

## Open questions
