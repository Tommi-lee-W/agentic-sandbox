# Plan for #2: Reject CO2 values outside 0 to 500 g/km

## Goal
- Reject any `co2GramsPerKm` outside the inclusive range 0..500 g/km.
- Keep valid boundary values accepted and preserve the current validation flow.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- Confirmed: `src/runs.ts` `validateNewRun` — change: yes. This is the validation gate for all submitted runs.
- Confirmed: `test/app.test.ts` `runs api` — change: yes. Add tests for out-of-range values and boundary acceptance.
- Confirmed: `public/index.html` form input — change: yes | no (decision pending). It posts the user-entered CO2 value; UI can enforce min/max too.
- Plausible: `src/app.ts` error mapping — change: no. It already turns `ValidationError.details` into a 400 response.
- Plausible: `e2e/smoke.spec.ts` — change: no unless browser UX is explicitly required.
- Open: product expectation for client-side validation in the page — change: depends on answer.

## Tests
- `test/app.test.ts`: add API validation checks for `-1`, `501`, `0`, and `500`.
- `e2e/smoke.spec.ts`: only if browser-range enforcement is required.

## Environment contract
- No new or changed environment variables. No `src/config.ts` or `k8s/configmap.yaml` edits.

## Risks
- Boundary confusion: 0 and 500 must be accepted; values just outside must fail with a clear validation detail.
- API/browser drift: server rejects invalid values, but the page may still accept or mislead the user unless min/max is also set.
- Pipeline risk: browser smoke tests still pass if form behavior remains compatible with existing inputs.

## Open questions
1. Should the browser form also enforce `min="0" max="500"` before the POST, in addition to the API validation?

## Decisions
- Decision 1: Only the API will enforce the 0..500 g/km range; the page does not need a client-side min/max attribute.
