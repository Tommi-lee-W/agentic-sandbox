# Plan for #3: Add DELETE /api/runs/:id

## Goal
- Add a DELETE endpoint that removes a run by id and returns the deleted record or a clear success response.
- Keep existing read and create flows unchanged; not-found behavior remains the same contract.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- Confirmed: `src/runs.ts` `RunStore` — change: yes. This in-memory store needs a delete method.
- Confirmed: `src/app.ts` route layer — change: yes. It defines `/api/runs` and `/:id`; DELETE belongs there.
- Confirmed: `test/app.test.ts` `runs api` — change: yes. Add success and missing-id tests.
- Plausible: `public/index.html` — change: no. There is no delete UI yet; the ticket is API-only unless a browser control is added later.
- Plausible: `e2e/smoke.spec.ts` — change: no unless the page is updated to expose delete actions.
- Open: response format for delete success — change: yes/no. The API contract is not specified in the issue; must choose between returning the deleted object or a simple `{ deleted: true }`.

## Tests
- `test/app.test.ts`: add DELETE success test and 404 test for unknown id.
- `e2e/smoke.spec.ts`: only if delete UI is added in the page.

## Environment contract
- No new or changed environment variables. No `src/config.ts` or `k8s/configmap.yaml` edits.

## Risks
- Deletion semantics: if the endpoint returns a deleted record, callers may expect to see its data; if it returns just a status, the UI/API contract is simpler but less informative.
- Route conflict with `GET /api/runs/:id`: DELETE adds a new path without affecting GET/POST behavior if implemented carefully.
- Pipeline risk: no environment changes; unit and smoke tests are the main checks.

## Open questions
1. What should DELETE /api/runs/:id return on success: the deleted run object or a minimal success payload?

## Decisions
- Decision 1: DELETE /api/runs/:id returns the deleted run object on success.
